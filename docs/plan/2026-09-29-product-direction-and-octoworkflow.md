> 日期：2026-09-29。研究方式：宿主源码核对、双账号 Pro 初评、宿主修订与一次 Pro 合并复核，总计 3 次有效评估。

## 1. 结论

**推荐有条件的第四条路线：把上下文核对的主要使用入口放进 OctoWorkFlow，保留 Contexpect 独立引擎、CLI 与仓库；暂不整体搬仓，不再优先扩张第二套完整桌面产品。**

当前最值得批准的下一步是最多 **5 个工程人日的独立价值试验**，不是批准完整集成。先证明引擎比原生诊断与现成工具多解决了什么，再花钱验证 OctoWorkFlow 入口。若不能证明，就转为第三条路线：保留资产、暂停新增投入。

若“合并”专指把 ContextView 全仓搬进 OctoWorkFlow，当前明确不推荐。产品方向、入口、引擎边界和仓库归属是四个独立决定。

| 选择 | 判断 | 原因与适用条件 |
| --- | --- | --- |
| ① 无价值关闭 | 当前不推荐 | 已有证据模型、解析与核对资产；没有证明其被完全替代，也未掌握现有用户和支持义务。功能未完成不等于无价值 |
| ② 独立维护并继续完善 | 不推荐按现有完整产品面全面投入 | 适配、同步、组织信任、实验、桌面和发行同时消耗资源，独立需求尚未验证；若独立 CLI 的真实重复使用成立、OWF 入口无增益，可改选窄定位的② |
| ③ 独立保留、暂停新增开发 | 明确退路；无试验资源时直接选它 | 保留历史、合同、导出与已承诺支持；不承诺追赶所有新版本。停止投资不冒充“完整交付” |
| ④ 纳入 OWF 使用场景 | 有条件首选 | 先验证能力，再验证入口；通过协议保留独立引擎，避免双重写入和两套完整工作台 |

## 3. 为什么保留能力、收敛产品面

### 3.1 两个项目解决的问题不同

Contexpect 回答：在指定工具版本、项目和 cwd 下，应加载哪些上下文？实际观察到了什么？哪些判断仍没有证据？OctoWorkFlow 回答：哪些受管能力安装到哪里？任务由谁执行、如何恢复？候选是否经过评审和门禁？

安装 receipt、任务 evidence 与 Context Receipt 可以关联，不能互相代替。Context Claim 与看板管理 claim 也不是同一种对象。源码依据：`crates/ctxpect-core/src/claim.rs` 的不变量；OWF `scripts/install_runtime.py` 的安装一致性核对；`workflow/owf_dashboard/observe.py` 的任务证据投影。

因此，Contexpect 的证据内核有保留价值；这不自动证明需要独立经营一整套桌面、后台、同步、策略、实验和发行产品。

### 3.2 当前最紧迫的是有效覆盖，而不是页面数量

| 本轮源码/记录事实 | 对投资的影响 |
| --- | --- |
| `ctxpect-resolve/src/lib.rs:141` 的 ANCHORS 只有 Codex 0.147.0 与 Claude Code 2.1.259，均为指定 macOS CLI 的 instructions | 版本语义适配是主要成本；不能把 frozen coordinate 当作当前工具支持 |
| `ctxpect-importer/src/lib.rs:85` 仅 DeepSeek Harness 分支读取专用 native JSONL，其余 mapping 走 generic JSON | 名称数量不等于原生格式支持数量 |
| `ctxpect-cli/src/native_oracle.rs` 明确 Codex 摘要 `provider_wire_payload=false`，Grok 未观察正文 | 原生诊断有价值，但不能声称当前真实任务已消费这些内容 |
| `ctxpect-store/src/lib.rs` 是 JSON ledger，SQLite/FTS5 是有记录的目标偏离 | 不应为入口整合先做数据库迁移；也不能宣传目标引擎已完成 |
| [运行接续记录](2026-09-12-runtime-and-release-execution.md) 的 E-LUNA-01 为 `inconclusive`，p=0.50 | 不能宣称改善模型效果；该实验也没有否定排障价值 |
| OWF README 的默认安装是按需 Skills；上述 resolver 解析 instructions | 第一版不能叫“OWF 安装全部生效检查”，不能为匹配工具而强推更多常驻规则 |

当前不存在用户数、活跃率、收入、支持投入的可靠数据。未知不是零，也不是继续全面建设的凭据。源码规模、测试数量和严格合同都不能代替用户价值证明。

### 3.3 原生工具在压缩基础诊断的差异空间

以下为 2026-09-29 一手网页核对，不是目标安装版本实测：

- Claude Code 官方文档提供 `/context` 加载检查，并注明原生 `AGENTS.md` 支持的版本门槛和观察边界。Contexpect 应解释、关联这些证据，避免另造脱离版本的猜测。[官方 memory 文档](https://code.claude.com/docs/en/memory)
- agnix 提供 agent 配置 lint 与 LSP；基础格式和规则问题不值得重复成为主要投入。[维护者仓库](https://github.com/agent-sh/agnix)
- Microsoft APM 已覆盖包来源、完整性和部署漂移；“磁盘文件与期望不同”也不是独占能力。[官方仓库](https://github.com/microsoft/apm)

Pro 另核对了 Codex 官方 `debug prompt-input` 文档，宿主在本仓 native adapter 中确认对应命令和能力限制。该诊断构造不能直接当另一实际任务的 provider 请求。外部资料支持替代压力，不支持“Contexpect 已被完全替代”或“没有市场”。

## 5. 先验证两种价值，再建设入口

采用三个条件，而不是只看集成后有没有点击：

| 条件 | 配置 | 要回答的问题 |
| --- | --- | --- |
| A | 原生诊断 + 适用的现成工具 | 不投资 Contexpect 已能解决多少？ |
| B | 相同基础 + 独立 ctxpect | 引擎是否提供正确的新解释、关联或核对效率？ |
| C | 同一引擎版本经 OWF 入口 | 相比 B，是否降低进入成本、提高事件发生时的主动复用？ |

### 阶段一：最多 5 人日，先不做 UI 桥

建议 3–5 个工程人日，含准备、必要适配、测试与复核，最迟第 2 周裁决。先选一个**实际正在使用**的 harness/OS 坐标和两个已授权项目；不要求用户降级、不把旧 pin 填到新工具上。现成工具也需先核对读写、网络和模型调用副作用。

建议至少收集 3 个可复核真实案例，覆盖 2 个项目，至少 1 例由非作者复核。每例记录原生方法能解释什么、ctxpect 增加什么、解释是否正确、是否改变下一步动作、人工核对时间与适配工时。新展示或更多 warning 不算增量；合成反例不能填真实需求样本。

5 人日是止损线，不是 adapter 完工承诺。当前坐标适配不完、样本不足、没有增量，分别报告；到限即停止新增投入。前两者只能证明“本轮未证明”，不能推断没有市场。可信的静态差异解释也能过首关，但只授权后续相应静态范围，不能假装已完成 native 闭环。

### 阶段二：B 有价值后，再批准 2–3 人日的入口试验

只做项目入口或已有任务旁的证据引用，允许最小原型验证 C；不迁移整个 Inspector、不接管现有配置、不创建空任务。B 通过不自动解锁剩余预算；C 未比 B 有用，就保留独立 CLI 路线。

### 阶段三：再次批准窄集成及验收

前两关成立后才编制实施合同，整体建议最多 6 周、30 人日，包含独立验证、版本适配、支持与收口。不是完整 F/WP 交付报价。首轮假设一名熟悉 Rust/Python 的工程师及少量前端与独立复核投入；缺这些条件就重新估算，不承诺固定日历完成。

后续建议累计至少 8 个可比真实诊断事件，正确解释的人工时间中位数较 A 降低 25%，解释正确率至少 90%；至少 3 名有重复需求者中 2 名主动再次使用 C，并说明入口或任务关联收益。8 个事件下正确率 ≥90% 实际要求 8/8，不将小样本阈值解释为普遍可靠性证明。

维护目标 ≤1 人日/周；没有真实版本变化则“适配维护未测”。性能在指定规模项目和硬件上测量，建议请求式扫描 P95≤15 秒；单次历史耗时不是基准。全部请求纳入分母，失败、超时、Unknown、授权不足和不支持分别统计；不删掉难例。顺序平衡、案例难度匹配，避免重复做已知答案的故障。上述阈值均是待批准的投入决策门槛，不是 causal Claim 或统计证明。

第 4 周复盘、第 6 周结束，不因样本少无限续期。越权写入、私密材料外发或静态证据升级为运行事实，立即暂停相关能力。

## 6. 通过试验后的具体接线方案

采用固定版本 `ctxpect` 的 one-shot 进程调用，OWF 做入口、参数、结果校验和关联；Contexpect 做语义判断。协议、能力声明和正式 Receipt 生成路径需要验证或补建，**尚不存在可直接宣称完成的 OWF 集成接口**。

输入限制到明确授权的项目/cwd/根目录，记录 engine 制品摘要、resolver、harness 版本及其来源、surface、OS、时间和输入内容摘要。dirty 文件身份不能只靠 HEAD。实际用户 profile 与隔离 probe profile 分开标注；不自动安装 hook 或读取历史私人会话。

输出分别处理执行失败、协议不兼容、未知、静态判定与原生观察。核实实际 JSON schema；普通 inspect 输出不由 OWF 伪装成正式 Context Receipt。Contexpect 自己生成持久化证据，OWF 仅存引用与展示缓存；过期或坐标不匹配明确提示。

新增触发子进程的接口属于控制能力，需使用适用的授权/认证与 Host/Origin 检查、固定 executable/argv、路径范围、输出上限、超时与进程清理。只读指不改被检项目和原生配置，允许授权的工具自有证据目录写入；子进程隔离本身不是权限沙箱。不因此改造所有既有只读页面。

| 对象 | 唯一写入 authority | 另一方边界 |
| --- | --- | --- |
| OWF canonical、受管文件、安装 receipt、备份/回滚 | OWF renderer/installer 原流程 | ctxpect 只观察，不直接修复 |
| Context Claim、正式 Receipt、ledger | Contexpect | OWF 展示和引用，不重写判定/签名 |
| 任务事件、预算、候选、评审与交付 | OWF 原任务流程 | Context 诊断不能自动宣布交付 |
| 新诊断关联 | OWF 版本化关联记录 | 不更改任务证据；不假定现有 relations 已适配 |
| 用户或 APM 管理配置 | 原 authority | 首轮只读，未来逐目标批准写入者 |

具体源码约束：OWF `install_runtime.py:1663–1666` 成功 doctor 会写回 `last_verified_at`，不能后台调用后声称无写入；读取旧 receipt 时须标本轮未复验。`check_delivery.py:41,430` 的 task 字段集合封闭，不能任意塞 `context_receipt`。同文件不同区块若均整体替换也会冲突，不能用区块边界推导并发安全。

首轮不代理现有 Contexpect daemon，不新增强制 gate，不将 Unknown 显示为 pass，也不让可选诊断擅自阻塞普通任务。现有 required gate/RED 保持。macOS/Windows 客户端先打开 Web 详情；有 Windows 客户端不等于引擎 Windows lane 已通过。

## 7. 停止、回退与改变判断的证据

| 新证据 | 决策 |
| --- | --- |
| B 优于 A，C 又优于 B，成本可控 | 继续④的窄入口与能力整合，不自动恢复全部原路线 |
| B 有价值，C 无收益；或非 OWF 使用者持续复用 | 改为②的独立 CLI/CI 工具定位；独立完整桌面另论 |
| 无增量、样本不足、适配/维护超预算 | 转③，标清是哪种原因，保留资产与支持责任 |
| 持续替代证据充分、无可持续使用需求或维护者 | 再申请①退役；先清点支持与数据保留，不删除证据 |
| 双仓联动发行成为实测主要成本 | 才讨论物理合仓；用协调成本证明，不以目录整齐为理由 |

回退只需关闭 OWF 入口/桥接、恢复兼容制品。试验用专用 store，原任务、安装状态和历史 Receipt 不变。关联停用可标记，不抹去权威证据。保留独立 CLI 与对应版本读取器；不让两个项目互相按另一套格式执行恢复。
