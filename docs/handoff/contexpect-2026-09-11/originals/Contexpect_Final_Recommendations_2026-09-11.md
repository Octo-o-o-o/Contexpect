## 一、最终核心决策

### 1.1 总体结论

**项目值得继续做，但应以“上下文为什么与预期不同，以及修复后验证到了哪里”为核心，而不是成为又一个配置管理平台。**

目前最值得投资的不是更多页面、更多工具名称或更多自定义格式，而是四种可以不断积累的资产：版本化原生规则、来源明确的运行证据、真实故障反例、可恢复且重新取证的修改流程。现有 Context IR、Claim、Receipt 与安全事务应成为承载这些资产的底座。[^truth][^projection]

| --- | --- | --- |

| 最终范围 | 保留 F-01–F-18、WP-01–WP-12 及冻结的必需适配范围 | 用双锚点演示替代完整交付；也不把所有新工具自动加进合同 |

## 二、产品定位与竞争策略

### 2.1 对外应该承诺什么

推荐产品表述：

> **Contexpect 是一个 local-first 的 AI coding context 诊断与核对工具。它针对具体工具版本、项目、工作目录和运行环境，解释哪些上下文预计会被发现或激活、哪些有运行证据、哪些仍无法确定，并帮助用户预览修复、控制修改和验证结果。**

面向用户的直接问题是：“为什么这条规则没有进入当前上下文？”“为什么换设备或换工具后不一样？”“这次修复到底只改了文件，还是已经取得了新的运行证据？”

不要无条件承诺看见完整隐藏 prompt、解释模型内部思维、保证所有工具行为一致，或证明每条规则必然提升质量。即使拿到了请求内容，也不能据此证明模型内部确实采用了某条规则。[^truth]

### 2.2 怎样面对已有工具

本会话核验的 CtxWise 已集中于 Codex 的审计、lock/drift 和测量边界；agnix 提供规则校验与多入口；APM 处理资产包依赖与来源；Rulesync 提供跨工具格式转换。它们分别覆盖 Contexpect 的若干组成部分，所以“没有一个完全同名同功能的产品”不构成竞争壁垒。[^ctxwise][^agnix][^apm][^rulesync]

**最终竞争策略是连接这些工作，而不是把它们全部重做：**读取包和配置来源，按原生规则解释预期，再与有边界的运行证据核对。跨工具差异、升级回归、工作目录变化和跨设备漂移，才是应该优先证明的增量价值。

对单一 Codex 的简单快照、泛用 lint 或普通配置生成，不预设 Contexpect 已经胜过专用工具。只有真实对照能证明它在哪些问题上更准确、更容易使用。

### 2.3 首批用户与价值验证

建议聚焦两类用户：有多个工具/设备/工作目录的重度开发者，以及承担团队环境排障责任的 Tech Lead / DevEx。复杂单工具用户同样值得服务，不必强制把“跨工具”作为使用门槛。

首先验证排障价值，再验证团队标准采用价值，最后验证统计优化和治理价值。是否收费、如何分层以及企业采购需求，应以实际试用与访谈为依据；本会话没有足够数据支持收入、市场份额或付费转化率预测。

依据来自仓库合同、测试和对应实现；这是基线判断，不是本轮重新执行全部测试后的结果。[^truth][^conformance][^importer][^doctor][^projection][^adr6][^sync][^architecture]

### 3.2 怎样解释现有覆盖数字

静态测试的 1,924 行分母是开发语料，不是等权产品需求。它区分实现通过、Unknown 诚实性通过、失败和未实现，并另列未执行的原生/封闭语料。不能据此计算一个看似精确的“产品完成百分比”。[^conformance]

同理，Doctor 在自己的语料上没有误报是必要护栏，但并不等于在实际项目中也没有误报。最终报告应同时展示规则适用范围、真实样本来源、未复核命中和已确认错误，不用一个总体绿色覆盖全部未知项。

## 四、必须优先澄清或修正的边界

### 4.1 原生预期、观察范围、用户期望必须分开

三者在现有 IR 中表达，不需要新建三套上下文对象。

| 概念 | 回答的问题 | 正确处理方式 |
| --- | --- | --- |
| 原生预期 | 这个版本的工具按其实际规则会发现、合并和激活什么？ | 由匹配版本的规则与输入推导 |
| 观察范围 | Contexpect 获准读取什么，实际检查了什么？ | 未授权、未读或读失败保留范围缺口 |
| 用户期望 | 用户或团队希望满足什么预算、来源和管理约束？ | 形成策略检查或修复目标，不伪造原生行为 |

例如，在 `.ctxpect-ignore` 中排除某文件，只能说明 Contexpect 不读取它，不能证明目标工具不会加载它。为 Claude 设置 Contexpect 自己的字节预算，只能产生预算超限或建议，不能在没有原生依据时产生“Claude 已截断”的结论。相关实现边界是本会话已经识别的优先复核项。[^research]

**验收性质：仅修改观察授权或 Contexpect 偏好，不应无证据改变原生行为声明。** 允许降低知识完整性，但不能把“不知道”变成“不存在”。

### 4.2 不要求字节相同，也不强制字节不同

本轮重新核对的语义对齐文档在 ST2 中含有对 Codex/Grok 的“native syntax/正文不得相同”要求。其防止机械复制冒充对齐的意图合理，但禁止相同文本本身过强。[^semantic]

**建议通过正式修订，改为：**不同工具可以产生相同或不同的文件内容；是否满足同一受限意图，取决于各自版本、scope、precedence、activation、能力与证据。字节相同既不充分证明语义等价，也不是语义不等价的证据。

在证明目标原生机制需要不同表达之前，不制造无意义差异。反过来，即使文件完全相同，只要 cwd 或加载规则不同，也不能直接判定一致。该修订应同步规范、生成器和测试，不能只改文字或只调整 golden。

### 4.3 Unknown 既不能被隐藏，也不能让所有安全动作永久停摆

保留 `truth_state` 的既有枚举；Unknown 的具体表达继续遵循 reason code、knowledge status 与 indeterminate，不新增一个同义且冲突的核心状态。[^truth]

需要分别回答两个问题：**这项结论是否已知？当前动作需要的前置证据是否齐全？**

例如，修复一个已明确解析的配置语法错误，不一定需要预先证明 Outcome-affecting；缺少运行快照也不一定阻止读取文件、查看 diff 或导出已允许的脱敏元数据。但目标文件归属不清、权限未知、批准已失效、关键策略求值失败，应阻止相关写入。

| 操作 | 必需前置证据的建议 | 仍可保持未知的部分 |
| --- | --- | --- |
| 只读检查 | 显式读取范围、支持的解析合同、资源限制 | 未暴露的运行面；结果标 partial/Unknown |
| 有限静态修复 | 目标身份、原始字节、修复语义、权限、策略、已批准计划 | 该规则是否提升任务质量 |
| 宣称模型可见 | 满足该声明的原生字段、来源、坐标与时间覆盖 | 模型内部归因 |
| 宣称运行时修复已核验 | 修改后对应运行实例的新证据及 required 检查 | 合同未要求的其他工具/会话 |
| 发布或采用团队标准 | 发布者信任、版本谱系、权限、适用坐标和例外 | 非适用的个人私有上下文 |

这不是降低 fail-closed，而是把 fail-closed 精确绑定到动作所需条件。未满足发布合同的 required 能力仍是交付缺口，不能用“诚实 Unknown”永久豁免。

### 4.4 声明文件不是独立运行证据

自有 `budget.json`、`inventory.json`、`plan.json` 等文件可以表达期望、声明或产品生成的结构化结果，但必须区分谁生成、何时生成、基于哪些输入以及是否由可信路径签发。当前 Doctor 文档明确有多项声明类规则。[^doctor]

一个文件写着 `truncated: true` 不等于原生工具已截断；写着 `approved: true` 不等于获得可信审批；`present` 数组列出某资产也不等于它当前存在。声明检查可以继续存在，但进入最终 Claim 或 mutation 授权前必须由相应证据链支撑。

优先让真实 collector、resolver、投影器和策略系统产生这些输入。无法接通生产者的规则应明确标注为“声明校验”，而不是继续包装成完整原生诊断。

### 4.5 历史 Receipt、现在的状态与当前规则解释不能混成一个答案

旧 Receipt 是过去一次观察的不可变记录。今天扫描磁盘得到的内容，不能回填为旧 Receipt 当时的状态；规则更新后重新分析旧证据，也不等于重新观察了过去的系统。[^truth]

建议所有衍生诊断绑定 `receipt_id`、分析规则版本、评估时间和新增证据引用。需要同时展示历史 Receipt 与当前扫描时，明确标为组合视图并列出两者时间，不能用一个“当前”标签消除差异。

同一原则适用于资产过期检查。基线 Doctor 的 stale 规则使用固定验收日期；最终产品建议把运行时 `as_of` 作为显式输入，而 fixture 通过注入时钟保持确定性。日期久只能证明超过某个维护阈值，不自动证明内容错误；旧规则历史结果仍可按原合同复现。[^doctor]

### 4.6 “单一写入者”是一项控制边界，不是对整个操作系统的保证

Contexpect 应协调自己及委托工具的写入，但用户编辑器、Git 操作和其他同权限程序未必遵守同一锁。文件摘要的前置比较再加 rename，并不自然构成可对抗所有外部写入的原子 compare-and-swap。

因此，规范要明确保护的是哪些参与者、哪些文件身份和哪些冲突窗口。使用受控根、锁、写前/写后核验、原子文件替换与持久 journal，并对不可消除的跨文件或外部写入冲突保守处理。不要承诺任意多文件修改天然原子，也不要将外部新编辑强行回滚。[^projection][^research]

### 4.7 独立回归测试要保护语义，而不是把所有现有 golden 永久神化

不允许为了让测试变绿而偷偷修改答案；但如果冻结规则本身有误，也不能永远禁止纠正它。正确路径是：新证据和最小反例 → 说明旧合同的问题 → 版本化修订 → 独立复核新的期望结果 → 更新实现与来源追踪。

对阻断规则，应有适用范围、确定性依据、独立反例和误报处理；不能仅靠自产语料 precision=1.00 就获得无限范围的阻断资格。规则疑似错误时先停止相应自动化，再做语义审查，不追求“永不红”的展示效果。[^doctor]

### 4.8 “一个账本”和“不可变”都需要正确解释

一个权威账本指同一个本地信任域中，Receipt、策略版本和事务状态不由多个数据库相互争夺解释权。多设备各自保有本地账本是正常情况，不需要发明一个全局单库；外部证据以带来源域的记录导入，不能覆盖本地已有身份。

不可变历史也不等于敏感正文永不删除。应保留最小 tombstone、出处与失效关系，删除被授权删除的正文及派生内容；无法召回的外部副本和操作系统残留必须明确说明。[^truth]

| --- | --- | --- |
| 领域合同与真值内核 | 坐标、IR、Claim、合法组合、schema、Receipt 核心语义 | M03、M05 |
| 采集与原生解释 | 文件边界、资产发现、版本化解析、原生导入 | M01、M02、M04 |
| 诊断与核对 | diff、drift、Doctor、等价条件与解释链 | M07、M08 |
| 受控管理 | 资产来源、意图投影、批准、写入、同步、团队标准与例外 | M09–M13 |
| 持久化与来源 | 本地账本、证据索引、迁移、删除、签名材料管理 | M05、M06 |
| 应用入口与运行管理 | CLI、daemon、API、调度、桌面、UI、运行诊断 | M14、M15、M18 |
| 分析与验证 | Advisor、历史洞察、实验合同、runner 结果与统计判定 | M16、M17 |
| 质量与发行 | 独立语料、属性/故障/E2E 测试、平台验证、发布与供应链 | M19、M20 |

### 5.2 推荐的核心工作流

```text
显式授权的文件、设置、原生日志、外部产物
                    │
             受控采集与输入校验
                    │
          ┌─────────┴─────────┐
          │                   │
     版本化原生解析       原生证据导入
     Expected + 来源      Observed + 覆盖
          └─────────┬─────────┘
                    │
        Contexpect Claim / Receipt 核对
                    │
              权威本地账本
                    │
           Diff / Doctor / Policy
                    │
          意图、修复或标准更新候选
                    │
        原生 renderer → 冻结变更计划
                    │
         身份、权限、策略、损失审批
                    │
           唯一变更协调入口
                    │
       文件级协调 / journal / 恢复保护
                    │
       修改后重扫 + 所需运行证据补采
                    │
       新 Receipt；未核验部分保持未知
```

CLI、桌面和 daemon 使用同一应用服务；不各自实现 policy、diff 或 Claim。Advisor 只产生建议，Effect runner 只提供受控运行结果，外部工具不能越过中间的授权与核对步骤。

### 5.3 四类所有权要登记清楚

| 所有权 | 关键问题 | 默认归属 |
| --- | --- | --- |
| 意图/资产源 | 应该修改哪份源？谁维护期望内容？ | 每个资产显式登记；可以是现有原生文件，不要求全部迁入新 manifest |
| 投影规则 | 谁负责将已批准意图表达成目标原生格式？ | 每个目标坐标选择一个权威 projector |
| 文件写入 | 谁真正修改这个物理文件或受管范围？ | 默认 Contexpect；准入通过后可明确委托，但不同时双写 |
| 最终核对 | 如何解释来源、覆盖、差异与验证状态？ | Contexpect 核心，且保留原始来源的不确定性 |

这不是要求现有用户立即迁移全部配置。初始接入应支持原生文件只读管理；用户决定采用受管意图后，再明确 source authority、overlay 和反向修改流程。

遇到一个物理文件同时服务多个 harness，应显式登记共享关系。即使两个工具管理不同 JSON 字段，也需要同一文件级协调；不能把字段所有权误当作不会发生整文件覆盖。

### 5.4 外部工具只有三种准入模式

**只读产物导入。** 用户提供报告或受控目录中的输出，Contexpect 验证格式、来源、坐标和隐私后导入。这是优先模式，不能顺便读取工具全部 home。

**隔离候选生成。** 工具处理冻结输入，只在专用 scratch 中生成文件与损失说明。它没有真实工作区写入权。scratch 只是目录隔离，不天然是沙箱；仍要限制环境变量、进程、网络和路径。

**受控委托执行。** 仅当指定版本能约束实际修改集合、执行范围、失败恢复和产物证据时开放。它成为相应目标的唯一实际写入者，Contexpect 继续持有外层授权和核对。无法满足合同则退回产物导入，不“先接再补安全”。

### 6.1 最终不进入默认运行时的项目

agentsync、Agentpack、chezmoi、Syncthing、Scopeon、ContextSpy 不作为默认整套后台服务。它们保留为设计、测试和按需产物输入来源，避免重复源状态、账本、备份、同步和权限。

OPA 不与 Cedar 同时成为核心批准引擎；promptfoo 不与 Inspect 在同一实验中隐式重复执行；OTel Collector 不成为个人版必须安装的组件。**不引入某个参考项目的完整运行时，不等于删去它对应的必需产品能力。**

### 6.2 不再继续横向搜索同类大底座

目前已有足够的对照对象，继续增加相似项目很可能稀释实施。下一轮选型只针对实际暴露的缺口：缺哪个原生输入、哪条路径保护不足、哪个迁移合同无法满足。一个新依赖应解决明确问题，并有可替换、可失败、可退出的边界。

## 七、依赖政策与基础设施的最终建议

### 7.1 建议正式调整目标，而不是偷偷绕开 ADR

ADR 0006 明确保持根 Rust workspace 零第三方 crate、延后 SQLite，并规定引入条件。它仍然有效；本建议不构成批准。[^adr6]

**最终推荐的目标是“少量、受控、可离线验证的依赖”，而不是永久零依赖。** 理由是项目的差异化在原生解释和证据核对；长期维护自写通用 JSON、schema、HTTP、存储和加密实现，会与这部分争夺资源。

建议在新的 ADR 中同时衡量功能缺口、误实现风险、维护负担和可审计性。不要把“理论上 std 绝对不可能实现”作为唯一触发条件；很多通用基础设施理论上都能自写，但并不因此值得自写。

### 7.2 依赖引入按必要性分三档

| 档位 | 候选 | 引入理由与条件 |
| --- | --- | --- |
| 安全/合同或明确完成目标相关 | 严格 schema 验证、文件能力实现、SQLite 绑定、标准加密实现 | 有具体缺口、迁移计划和独立测试；优先审查，不意味着一次全部替换 |
| 维护效率相关 | Axum、notify、tracing、proptest | 能减少已出现的维护问题；不为整齐而重构全部核心 |
| 复杂度增长后才考虑 | Cedar、Rig、TanStack Query | 先证明现有实现遇到真实瓶颈，再引入底层实现或请求层 |

每项必须固定版本/commit、features、工具链兼容、传递依赖、许可证、离线材料和退出方式。根 workspace、桌面 workspace、前端、开发工具与 sidecar 都要登记，不能只盯 Cargo.lock。

### 7.3 三条不得因换库而丢失的约束

**序列化兼容。** 替换 JSON 或 schema 实现不得隐式改变旧 Receipt 签名字节、数字词素和校验规则；旧算法继续只按旧规则验证，新合同明确版本化。

**默认行为最小化。** jsonschema 当前的默认 feature 含外部 HTTP/文件引用解析；接入时应禁用不受控引用并固定 schema registry。一个库“更标准”不等于它的所有默认能力符合离线边界。[^jsonschema]

**迁移只有一个写入权威。** JSON → SQLite 可先离线对照、重建索引与验证结果，但不能长期让两种引擎互相双写。切换前冻结一致性快照，失败时保留明确恢复点；切换后新写入的回退必须走经测试的导出/兼容流程，不能简单换回旧程序。SQLite WAL 也不能当作跨机共享数据库方案。[^sqlite][^research]

## 八、必须先做成的用户闭环

### 8.1 闭环 A：复杂目录中的规则为什么没有进入预期上下文

用户选择项目和实际 cwd；Contexpect 展示根到工作目录的规则来源、覆盖、导入、激活条件与未知项。问题出现时，指向具体文件、规则和坐标，而不是只列出文件树。

优先覆盖已有 Codex/Claude 锚点的真实高频情况：根标记、全局/项目层、嵌套目录、显式 import、配置覆盖、按路径规则和能力未支持。具体行为严格来自对应版本，不把不同工具规则合并成通用想象。

**通过标准：**未参与实现的人能在相同输入上复现解释；系统给出规则依据，并明确哪些是静态判断、哪些有运行证据。原生面不可用的工具保持诚实，不能用模拟输出代替。

### 8.2 闭环 B：改了配置，正在运行的会话为什么仍不一样

将磁盘快照、会话实例、请求/turn 和采集时间关联。新磁盘状态不能自动更新旧会话的观察事实。对于热加载、懒加载和仅启动加载，只有适配器合同支持时才作明确判断。

**通过标准：**可以区分“文件已改”“静态预期已变”“原会话没有新证据”“某次新请求观察到变化”。缺少对应请求证据时不给出模型已加载的暗示。

### 8.3 闭环 C：两个工具采用同一意图，但保留必要原生差异

从有限、结构化的意图开始，分别生成原生候选和损失说明。不能表达的项返回 unsupported/loss，不能用 LLM 改写后的相似文字冒充已证明等价。

**通过标准：**内容相同或不同都允许；每个目标的 scope、激活方式和权限边界独立检查。写入后各自产生新 Receipt，运行证据缺失的目标明确标记。

### 8.4 闭环 D：预览后用户又修改了文件，系统不会误覆盖

同一份已批准计划绑定原文件、目标身份、策略、例外与有效期。执行前发现修改，转为重新预览或协调；网络重试不重复 apply；rollback 不覆盖用户后续编辑。

**通过标准：**并发、取消、崩溃与部分写入都有可解释的状态；用户始终能知道什么已改、什么未改、什么需要人工确认。

### 8.5 闭环 E：团队标准跨设备采用，但私人内容不被默认披露

技术负责人发布有信任来源和版本谱系的标准；成员查看变更与披露范围，采用时走同一投影和事务。同步只搬运允许的 bundle，不自动复制会话、凭据、活动数据库或私钥。

**通过标准：**离线分叉不自动 LWW；被移除成员无法获得新授权材料，但系统不承诺召回其旧副本；负责人只获得事先约定的合规与证据元数据。[^semantic]

这五条闭环是产品深度验证的优先顺序，不替代完整 WP-12。团队身份、同步和 Effect Lab 可以并行准备合同与测试，但不能提前发明新的对象或绕过共享内核。

<a id="implementation"></a>

## 九、关键实现要求

### 9.1 Adapter：从“工具名列表”变成可维护的版本合同

每个能力单元绑定 `family × version × surface × capability`，并明确适用 OS/environment、输入格式、规则来源和测试证据。新版本未知时，保留可安全读取的基础元数据，但依赖未知行为的 Claim 不得沿用旧版本结论。

每个 adapter 至少明确：静态解析支持哪些字段、原生导入支持哪些字段、哪些需要执行授权、哪些已完成真实互操作、哪些只验证了格式。安装探测、授权状态、工具版本和 evidence capability 分开呈现。

更新按“上游变更 → 对应版本样例 → 差分测试 → 新版本声明”推进。无需为所有工具建立同一个万能解析器，也无需为每个工具复制整个产品栈。

### 9.2 原生导入：最小证据桥，而不是另一个日志中心

读取对象、序列、日志轮转与会话身份应有版本化合同。来源域、工具实例与 session/request ID 共同确定身份；重复导入幂等，损坏或缺段降低覆盖，不拼造缺失事件。现有 DSH 专用路径不能被降格成“所有格式都转成同一 events[] 就算支持”。[^importer]

注意原生日志的真实性边界：从用户可修改文件导入的记录，不因格式与原生一致就天然防篡改。原生格式来源、采集通道可信度、内容完整性和签名身份应能分别解释。

当证据不足时，给出获取下一项证据所需的最小动作及权限，而不是让用户自行研究所有日志位置。若该动作会运行工具、联网或产生费用，必须先展示。

### 9.3 Doctor：范围先于规则数量

诊断至少分开事实、风险与建议；严重程度、确认程度、是否阻断与是否可自动修复各自有合同，不把 Unknown 当成严重程度。

每条规则应具备适用版本、必要输入、前置覆盖、触发依据、正常反例、所需权限和修复风险。两条指令看起来相反，但 scope 不重叠或不可能同时激活时，不应自动确认为冲突。较旧的文件、相同文本或某个工具不熟悉的字段，也不应天然算错误。

agnix/Gitleaks 等输出只能按已验证字段映射为 finding。扫描未执行、执行失败、解析失败、范围不全与没有命中必须分开；工具自己的 allowlist 或仓库注释不得自动成为 Contexpect 的可信例外。[^agnix][^research]

### 9.4 Mutation：状态与核对结果分轴

建议用可恢复状态表达计划、批准、执行、部分写入、提交和回滚；具体命名复用现有 schema，不强行新增一套同义状态机。关键要求是：

- 执行的是已经冻结的计划，不在 apply 时重新生成内容。
- UI、CLI、同步和外部工具的修改统一进入相同授权路径。
- 同一操作 ID 的重试返回已有状态，不悄悄重复消费。
- 持久 journal 先于不可恢复副作用，恢复必须验证目标与 before/after 记录。
- 写入成功、静态重验通过、运行时核验通过是不同结果；回滚也产生新的后续观察。

**“已写入，运行时未验证”是合法而有价值的结果。** 不应被错误显示为写入失败，也不能显示为完整生效。[^projection][^truth]

### 9.5 元数据优先：仍然需要处理摘要与旁路日志

没有保存正文，不等于没有隐私风险。路径、文件名、token 计数、资产名称、未加密摘要和相同摘要之间的关联，都可能泄露信息。对低熵内容的公开裸摘要尤其不能当作天然匿名化。

按本地身份、跨设备比较、公开导出分开定义摘要域；不要为方便 diff 而到处复用同一个密钥或直接开放内容 hash。不同设备的 keyed digest 不可比较时，就按公开的 EquivalenceProfile 使用允许字段或明确不可比较，不能把“两边都 Unknown”视为已证明相同。[^truth]

删除需要影响索引、派生建议、实验引用、备份与本地缓存，但旧 Receipt 的最小历史完整性记录不被悄悄改写。外部原始文件是否删除是独立授权，不能因为删除一条导入记录就顺便删除用户的原生日志。

### 9.6 团队可信身份：不要把本地批准包装成组织背书

保留本地连续性验证的价值，但不要让本地 HMAC、浏览器自报角色、用户可编辑的 principal 文件或包安装成功，直接代表组织授权。团队标准签名必须和可信发布者、用途、版本、撤销与离线新鲜度绑定。[^truth][^semantic]

是否能强制执行要单独报告。在没有管理通道的环境中可以做 detect-only，但不能宣称能阻止用户绕过。管理员视图也不应为了完整性自动要求上传私人正文。

如未来引入 Cedar，关键策略 errors 不能被忽略后让其他 permit 放行；其官方语义明确采用 skip-on-error 并在 diagnostics 中报告。Contexpect 应先验证请求与 required 证据，必要时阻止该动作，而不是修改上游语义后还假称原生 Cedar 行为。[^cedar]

### 9.7 同步：只传输，不替代语义仲裁

以既定 folder/Git provider 传输不可变 bundle；目录中只放已批准内容，不包含数据库热文件、授权 token、签名私钥或明文备份。收取后先验证 schema、内容绑定和信任，再判断父 revision、重放与分叉，最后进入正常投影流程。

加密解决保密，签名解决身份与完整性的一部分，版本谱系解决回退和分叉；三者不能互相替代。无法验证新鲜撤销状态时，说明离线信任材料的时间边界。[^age][^semantic]

### 9.8 API 与桌面：不要新增快捷旁路

本地 API 仍需身份、scope、Host/Origin 与请求边界。桌面 capability 不自动保护 HTTP，绑定 loopback 也不是对全部本地进程的授权。

Tauri 不应增加直接读写配置或 SQL 的旁路，UI 不缓存另一份最终真值。查询缓存应绑定所有影响结果的输入；副作用请求禁止自动乐观显示合规、verified 或已生效。

当前官方文档已给出覆盖 macOS 的内嵌 WebDriver / `@wdio/tauri-service` 路线；它是值得验证的桌面测试方案，不是项目已完成的平台证据。真实端到端测试使用真实后端，测试插件和 mock 能力必须从发布构建剔除。[^tauri]

### 9.9 Advisor 与历史洞察：建议不参与事实自证

只发送用户批准的最小分析包，说明包含的项目、时间窗、字段、成本边界与不可见项。结果只写入建议对象，引用实际存在的证据；原证据删除或失效后，建议也应标记失效。

模型建议执行操作时，重新进入相同 preview/授权流程。不要引入完整自主 agent、向量记忆或工具调用链来实现一个建议器；Rig 仅是按需的 provider 抽象候选。[^research]

### 9.10 Effect Lab：执行器、评分器与统计程序分离

保留冻结合同；外部 runner 负责运行与如实记录，不决定 Contexpect 的效果声明。Inspect AI 是优先研究的 runner，但其日志可能包含输入、转录和错误 API 数据，因此必须先验证受限日志流程，再批准真实运行。[^inspect]

现有 v2 估计器应保留算法版本和历史可复算性，但“已经冻结”“实现很短”都不等于独立证明正确。建议补独立数值对照与覆盖率/错误率检验，尤其检查组合区间、边界样本、等价检验和多重比较；本建议不是断言现有 v2 已被证明有错误。[^adr6]

质量通过率、时间、成本是不同类型的结果，不应强行套入一个二项估计器。为连续型结果增加判据时，另行冻结合同；原先不支持时如实报告。缓存、环境漂移、配对随机顺序、失败与重试、任务污染、评分器版本和额外样本都必须进入运行记录。

有 metadata Receipt 不意味着能完整重放过去任务；若复现实验还需要原始输入、模型服务或工具环境，必须说明依赖并重新获得授权。不要将某一次受限实验的收益推广为所有项目的通用效果。

## 十、实施顺序、依赖与停止条件

### 10.1 按门槛推进，不虚构工期

以下阶段是对既有 WP 的实施组织，不新增 WP-13，也不修改原完成条件。没有团队规模、人员能力和当前分支差异的数据，因此不提供看似精确的周数、人日或完成率。每一阶段以产物与退出条件管理。

| 阶段 | 主要交付 | 前置依赖 | 退出条件 | 未达到时不得做什么 |
| --- | --- | --- | --- | --- |
| D0 基线与语义收口 | 实现/支持/执行证据矩阵；第 4 章修订项；来源与文档同步方案 | 固定代码与现有合同 | 观察范围、原生预期、策略、历史与当前状态不再混淆 | 不新增依赖来掩盖模型问题，不宣传完整支持 |
| D1 双锚点与证据纵向验证 | 已有 Codex/Claude 的真实静态输入、关键导入、最小真实故障集；至少对可取得的原生面补证 | D0 | 外部人员能复现；事实与 Unknown 清晰；至少一条真实证据桥连到 Receipt | 不以 synthetic、mapping 名称或 UI mock 冒充原生支持 |
| D2 Doctor 与用户路径收口 | 真实输入驱动诊断；APM 等只读产物导入；Doctor→证据→计划的可用路径 | D1 合同稳定部分 | 正常反例不会被错误自动修复；未知、失败和无命中分开；关键 E2E 可复跑 | 不启用外部工具直接 fix 或自动安装 |
| D3 基础设施有条件替换 | 必要依赖准入、离线材料、存储/文件/schema/API 单项迁移与回退 | D0；可与 D1/D2 非冲突部分并行 | 每项独立通过历史兼容、平台与故障测试 | 不同时切换全部基础设施，不长期双账本 |
| D4 管理、同步与团队信任 | 有限 native 投影、安全 apply/rollback、标准版本与例外、加密 bundle | D1/D2；需要的 D3 能力完成 | 冻结计划可恢复；post-Receipt；分叉不自动覆盖；身份边界真实 | 不用本地 MAC 冒充组织证明，不把传输当核验 |
| D5 全矩阵、分析与发行 | 扩展冻结适配范围；历史/Advisor/Effect；桌面与所有必需 OS、soak、人工及发行验收 | 相关共享合同稳定 | F/WP 所有必需项按原合同通过，独立 readback 完成 | 不把阶段试用版称为完整产品 |

**双锚点的“做深”不要求伪造两个工具都开放完整运行时接口。** 对能取得且合同要求的原生面真实验证；对确实未暴露的面保留 Unknown 并说明原因。适配矩阵中原本 required-supported 的能力不能因实现困难改成 required-unknown-honesty 来消除缺口。

### 10.2 可以并行与不应并行的工作

可并行：不同 adapter 的原生资料与独立样例、UI 无障碍测试、文档状态生成、外部产物合同设计、独立加密/签名准入验证。前提是共用对象与退出条件已经明确。

不应并行大改：核心 Claim/schema 与全部前端 DTO、存储引擎与签名字节、多个真实写入器、多个策略引擎、完整 UI 请求层和 API 路由重构。否则发生回归时难以定位，更容易让测试与实现同步漂移。

一个外部候选不合适时，应替换实现、缩小接入权限或保留只读输入；不能因此把它对应的必需产品能力永久删除。

### 10.3 立即停止扩张的信号

出现以下任一情况，应暂停相关新功能，先处理根因：旧 Receipt 无法验证；未授权读取或旁路落地正文；同一目标出现两个写入 authority；Unknown 被转换为通过；真实配置正常但被阻断为确认错误；无法确定某次修改到底写了哪些文件；同一查询在 CLI 与 UI 中得到不同事实。

这里的停止针对受影响的能力，不必让无关的只读检查和历史导出全部不可用。恢复要以负例转红、修复后再绿和独立复核为依据。

## 十一、统一验收标准

### 11.1 四种证据分别记账

| 证据类型 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 合同/静态检查 | 文件结构、schema、需求追踪正确 | 产品运行时已经实现 |
| 单元/集成与生成语料 | 当前实现符合已写出的输入与规则 | 真实世界样本充分、目标工具行为一致 |
| 对应版本的原生互操作 | 特定坐标与输入下，本地解释与原生面一致 | 所有版本、所有平台和隐藏面都一致 |
| 独立用户/跨平台/长时间验收 | 使用路径、安装、恢复、可用性在明确范围内成立 | 范围之外也自动成立 |

覆盖报告保留 implemented-pass、unknown-honesty-pass、fail、unimplemented 等既有分桶；“未执行”作为相关测试范围的状态另列，不混进同一个成功分母。每个比例都附分母定义，不展示混合的总体健康分。[^conformance]

## 十二、怎样验证产品价值，而不是只验证功能

### 12.1 建议使用的指标

这些是建议采集的指标，不是已经测得的表现，也不预设通用阈值。

| 指标 | 计算或记录方式 | 防止误读 |
| --- | --- | --- |
| 首次有效诊断完成率 | 用户选择项目后，能否得到有依据的解释或明确的最小补证动作 | 不能把“看到界面”当有效完成 |
| 解释耗时 | 从提出具体问题到确认原因，记录中位数及长尾 | 与相同任务的原生命令/现成工具基线比较 |
| 确认错误的诊断精度 | 人工核验的确认问题中真正成立的比例 | 未复核命中单列，按规则与场景分组 |
| 修复闭环率 | 获准修复中，成功写入、静态重验、运行补证分别计数 | 三个比例不能混成一个“生效率” |
| Unknown 的可处理性 | Unknown 是否解释原因、是否有最小补证路径、补证是否解决 | 不以降低 Unknown 数量为目标鼓励猜测 |
| 漂移排障收益 | 已确认不一致事件的排查时间与重复发生情况 | 文件改动数量不等于问题数量 |
| 独立复现率 | 非实现者能否按同坐标与输入复现记录结论 | 维护者重复运行不是独立复现 |
| 适配维护成本 | 上游变化到恢复受支持状态的工作量、真实回归数量 | 不只看适配器名称增长 |
| 使用后留存价值 | 用户是否在后续真实故障、升级或团队采用时再次使用 | 演示点赞不等于长期需求 |

### 12.2 试用方法

从闭环 A–E 选择真实问题，先记录用户原来的排查方法，再使用 Contexpect 比较。单次试用避免同时大幅修改规则、模型、工具版本和项目代码，否则难以判断价值来自哪里。

每个公开案例应包含问题、适用坐标、数据脱敏方式、原始基线方法、Contexpect 的证据链、修复范围和仍未验证的部分。优先展示“准确解释并避免误改”，不要只展示 token 下降或截图更漂亮。

早期形成性试用可验证方向，但对外明确它与完整交付验收不同。若某个场景连续只返回不可处理的 Unknown，或不比已有工具更省事，应改善该场景的数据与交互，而不是扩大支持列表掩盖问题。

### 13.1 建议下一批实际工作

优先完成 T01/T02，然后以 T03/T04/T05/T06/T09 的交集做一条真实纵向闭环。T07 可并行准备决策与离线材料，但不要先进行大范围换库。T08 先接只读产物，避免过早承担外部执行副作用。

如果必须在“再加一个 adapter 名称”和“让现有一个真实问题从诊断到修复可独立复现”之间选择，优先后者。完成该闭环后，把已稳定的测试与接口复制到其余冻结 family，而不是重新发明流程。

### 13.2 每个任务完成时必须交付的说明

简要说明改了什么、没有改什么、对应哪个 Feature/WP、输入输出合同是否变化、来源版本、实际执行的测试、未执行项、已知风险与回退方法。不能只提交“完成”“全部绿色”或大段解释而没有证据。

代码审查优先查看安全边界与反例，再看界面截图和功能数量。实现者与复核者可以协作，但对关键结论应保存独立判断过程所使用的输入和结果，不把同一次交付中的角色切换包装成完整独立验收。

## 十四、文档、治理与防止再次过度设计

### 14.1 不再维护多套相互矛盾的状态文字

复用现有 compatibility、traceability、integration-contracts 和测试记录，生成或校验 README 的实现状态、UI capability 标签和发布说明。对冻结 schema/算法建立版本关系；对阶段记录保留历史，不追改成今天状态。

规范不应因为一句顶部“尚未实施”抹掉已有实现，也不能因为一个 crate 已创建就宣称全功能完成。所有状态都附 scope、基线与证据位置。

### 14.2 只为消费者新增抽象

本报告提到的外部报告、proposal、mutation 请求和实验结果字段，应先映射到已有对象。确有缺失再做版本化扩展，不一次新建一套与现有 schema 平行的协议。

不要为了“以后会用到”新增图数据库、CRDT、云账号、消息集群、plugin marketplace、向量库或统一 agent runtime。也不要要求每条纯只读分析都经过重量级常驻 daemon。

### 14.3 关键新增建议如何进入仓库

| 建议 | 应进入的既有位置或机制 | 不能直接做的事 |
| --- | --- | --- |
| 原生/观察/策略分离 | data-and-truth-model、adapter grammar、Claim 测试 | 新造一套同义对象后让旧接口继续错误输出 |
| 不强制不同文本 | semantic-alignment-and-team-standard、相关生成器与样例 | 只改测试答案而不说明合同修订 |
| 时间与历史视图 | Receipt 派生分析、Doctor 参数、API/界面合同 | 回写旧 Receipt 让其看起来永远 current |
| 动作级 required 证据 | policy、mutation 请求与审批合同 | 把所有 Unknown 都全局放行或全部禁用 |
| 依赖政策调整 | 正式 superseding ADR、锁文件、离线与许可门禁 | 将本文视为新增依赖的自动批准 |
| 真实语料与阻断资格 | doctor-rule-map、test-strategy、conformance | 依自产样例百分比直接扩大规则适用范围 |
| 桌面测试路线 | 独立桌面测试构建与发行检查 | 将 WebDriver/IPC mock 带进产品包 |

### 14.4 应保留的取舍记录

每项外部依赖说明为什么不采用最强的完整产品、为什么选择较小的接口、什么情况下需要更换。记录的不只是“选了什么”，还包括它无权做什么、失败时如何保持历史可读、如何退出而不损失用户原生配置。

<a id="final"></a>

## 十五、最终建议

**继续做，不建议整体推倒重建，也不建议把多个相关产品完整拼在一起。** 保留当前有价值的真值模型、安全事务和 local-first 方向；优先修正容易制造错误结论的边界，再让真实工具输入与真实反例充实它。

**对投入的最终排序是：正确解释 → 真实补证 → 安全修复 → 独立复现 → 规模化适配 → 团队与分析能力的完整兑现。** UI、测试和发行应与主线并行推进，不等所有后端功能完成才开始；但它们不能替代事实与安全合同。

基础设施可以借助成熟项目，核心语义不能外包。包管理器证明安装，renderer 产生候选，检测器报告命中，签名器证明身份与字节关系，runner 报告运行结果；Contexpect 的职责是把这些不同强度的输入放回同一个坐标和证据模型中，拒绝将局部成功夸大成完整生效。

最终应被用户记住的不是“它支持很多工具”，而是：

> **当 AI 工具的行为与配置预期不一致时，Contexpect 能说清差在哪里、证据是什么、哪些仍未知；需要修改时不会乱改，改完后也不会夸大验证结果。**

这是本会话全部调研收敛后的主建议，也是今后判断每一个功能、依赖、抽象与发布声明是否值得保留的标准。
