# 产品定位、竞争判断与价值验证

**状态：本会话研究结论的归档重组。** 不扩展最终产品范围，不把历史外部资料当成最新评测；详细依据保存在两份原文和来源台账。

## 1. 最终定位

Contexpect 是 local-first 的 AI coding context 诊断、核对与安全管理工具。它在具体设备、工具版本、项目、cwd、会话和任务下解释：哪些上下文按原生规则预计出现，哪些有运行证据，哪些仍不确定；再帮助用户预览修复、控制修改并核对修改后的结果。品牌主张保留 **Expected. Observed. Reconciled.**，CLI 名称保留 `ctxpect`。[^R2]

主问题不是“把所有配置放到一个后台”，而是“为什么这次上下文与预期不同，证据是什么，应该怎样修复，修复后验证到了哪里”。不要把产品改成通用电脑环境体检、IDE 插件安装器、shell/Git 设置管理器或自动换模型工具。它们只有在与具体上下文问题有关时，才作为环境坐标或输入出现。

## 2. 当前竞争力：方向有差异，尚未建立已经验证的壁垒

本会话识别的价值基础是：版本化原生规则、六个独立证据面、Unknown 与覆盖语义、不可变 Receipt、可解释 diff，以及预览绑定、受控写入、恢复和后续核验。已有工程不应被“只是文档”抹掉，但适配名称、源码目录和合成语料也不能被算作全部能力已完成。[^R2]

真正可能积累的优势，是对应版本的行为样本、真实事故的最小反例、可靠的证据映射和独立复现案例。Receipt、local-first、lint、同步或漂亮 dashboard 单独都不足以构成独有卖点。

## 3. 竞争对象与对应取舍

下表归档本会话已调研的能力边界；未对所有产品重跑构建、压力或安全审计。不用 Star、规则数量或维护者自己的基准作质量排名。[^R1]

| 对象 | 本会话研究的主要能力 | 对 Contexpect 的影响 | 最终取舍 |
| --- | --- | --- | --- |
| CtxWise / FramY2/ctxwise | Codex 审计、lock/drift、profile、测量边界与 receipt | 单工具快速诊断已有集中式替代 | 学 root-to-cwd、解释与复现；不引入第二份基线权威 |
| agnix / agent-sh/agnix | 规则校验、解释、修复分级、多入口 | Doctor 不能只是入口更重的 lint | 学规则元数据和正常反例；外部修复不直接执行 |
| Microsoft APM | 上下文包、依赖、lock、来源、审计/SBOM | 不应重做包管理和安装治理 | 优先只读导入产物，写入须另行准入 |
| Rulesync | 多工具原生配置转换/生成 | “同一份规则生成多个文件”不是空白能力 | 隔离候选 renderer；不接管真实配置 |
| agentsync | 源/实际/上次应用对账、有损映射、双向管理 | 与自有 authority、备份、同步明显重叠 | 保留设计参考，不默认运行完整系统 |
| Agentpack / chezmoi | 受管状态、preview/diff、部署/回滚和机器差异 | 安全修改有成熟模式可学 | 借鉴事务与状态模型，保留自有协调器 |
| Scopeon | provider 增量日志、会话/turn 指标、监测 | 会话统计和成本图表已有替代 | 学解析与轮转，不合并私有数据库 |
| ContextSpy | 请求级 profiler、捕获与请求组成分析 | 更直接的捕获会改变权限与隐私成本 | 仅显式授权的外部诊断/导出来源；不默认 MITM |
| 原生 harness 的诊断与配置入口 | 单工具最接近自身行为的证据面 | 原生能力完善会挤压单工具查看器价值 | 优先利用原生面，专注跨坐标核对而非替代原生设置页 |

具体阅读入口与来源见 [来源台账](13_SOURCES_AND_EVIDENCE.md)；能力细节和限制见 [逐环节调研](04_MODULE_RESEARCH_AND_SELECTION.md)。[^R1]

**最现实的竞争不是某一个同名产品，而是“原生命令 + 配置工具 + 用户人工排查”的组合。** Contexpect 必须证明自己减少了排障成本、误判或误改，而不是只把已有输出搬进一张更大的界面。

## 4. 亮点、不足和缺口分别是什么

| 分类 | 会话结论 | 下一步应沉淀的东西 |
| --- | --- | --- |
| 亮点 | 不混淆存在、发现、可见、使用和效果；重视来源与 Unknown | 把每个摘要与 UI 标签绑定到实际字段和坐标 |
| 亮点 | 已有可追溯预览、事务、回滚保护，DSH 有专用导入路径 | 保留已有负例和限制，不在换库时回退 |
| 不足 | 两个 instructions 切片较窄，原生复杂层级/输入尚不充分 | 深化已有锚点、对应版本样例和真实字段映射 |
| 不足 | 部分 Doctor 规则主要依赖自有声明，泛化还未证明 | 声明校验与实际诊断分列；接通输入生产者 |
| 不足 | 已有规范过强或模糊之处可能制造错误解释 | 按最终建议修订，不以冻结为由保持错误 |
| 缺口 | 真实 Expected→Observed→修复→新证据的可重复链路 | 至少一条真实证据桥与外部可复现案例 |
| 缺口 | 组织信任、完整同步、全矩阵和用户收益尚需验证 | 分别完成既定合同，不用界面或本地签名提前宣称 |

这张表是基于本会话固定提交的分析，不是对未来仓库状态的断言。[^R2]

## 5. 优先用户与核心场景

首先服务被复杂上下文困扰的重度开发者，以及承担排障和规范落地责任的 Tech Lead / DevEx。复杂单工具、monorepo、多 cwd/worktree 用户也应能获得价值，不强迫用户先用多个 agent。[^R2]

优先验证五条路径：复杂目录的规则解释、配置改动与旧会话的差异、受限意图的跨工具表达、预览后外部编辑的冲突保护、团队标准采用与私人内容隔离。不是先建更多菜单或云功能。

## 6. 价值如何被证明

建议记录首次有效诊断完成率、解释耗时、人工复核精度、写入/静态重验/运行核验分段完成率、Unknown 的可处理性、独立复现率和适配维护成本。它们是待测指标，不是已取得的成绩。[^R2]

同一真实问题先保留用户原排查流程，再对照 Contexpect。不能同时换模型、工具版本、配置和项目代码后把差异全部归因于本产品。公开案例应展示坐标、输入范围、原方法、证据、改动与剩余未知。

不在本包提供收入、市场份额、付费转化或“普遍提高代码正确率”的预测；当前材料不足以支持这些结论。演示满意是视觉反馈，不等于长期产品留存或已完成市场验证。
